# Look-alike Quiz Engine with Per-Species Mastery

## Intent

MycoMatch should teach people to tell look-alike mushrooms apart in the field. Today
it can't: wrong answers are random species from the same batch of 50 recent
observations, so a chanterelle question might offer a lichen and a bracket fungus,
and you can answer by elimination. Beginners also need a gentle start, so the
difficulty has to ramp up as they learn.

This change replaces how questions are built:

- Distractors range from "obviously different" to "real field look-alikes".
- Difficulty ramps automatically, **per species**. A species you just met shows up
  against easy distractors. As you keep getting it right, it shows up against its
  true look-alikes.
- Progress persists across sessions.

## Goals

- Hard questions use real look-alikes, sourced from iNaturalist's
  misidentification data (`/v1/identifications/similar_species`).
- Each species climbs its own ramp based on the learner's answers. The learner
  never picks a level.
- Beginners meet common species from their region first.
- Answers are always species-level, never genus or higher.
- A quiz loads about as fast as it does today. PROJECT_PLAN.md's target is under 2s per
  question.

## Non-goals (planned as later, separate projects)

- A side-by-side comparison of your pick versus the right answer after a miss.
- Scheduling with spaced repetition. This project *records* confusions so that
  work can use them later, but doesn't schedule reviews.
- Field-context clues (substrate, month) and toxic look-alike warnings.
- Accounts or cloud sync.
- A full "collection" page listing every species.
- Manual difficulty override. (My call: the ramp is automatic only for v1, plus a
  "reset progress" action.)

## Anti-goals (would be failures even if it technically works)

- Hard-tier distractors from another continent *when local look-alikes exist*. A
  Western NA learner being asked to separate Amanita muscaria from a species that only
  grows in Australia isn't field practice. Non-local look-alikes are only filler for
  when the local ones run out (see Distractors).
- A noticeably slower quiz, or the quiz breaking when iNaturalist is slow.
- Losing the existing "resume a quiz in progress" behavior.
- Promoting a species on a single lucky guess.

## Constraints

- iNaturalist rate limit: ~100 requests/min. Don't fan out one call per species
  per quiz.
- Hosting is AWS Amplify (`amplify.yml`). Next's data cache (`fetch` with
  `next: { revalidate }`) has to actually work there. Verify this **first**, by
  deploying a throwaway cached route on a feature branch (Amplify Hosting gives
  connected branches their own URL. If the branch isn't auto-deployed, ask the user to
  connect it in the Amplify console). Put all caching behind one small helper so that if
  the data cache doesn't work, switching to an in-memory TTL cache touches only that
  helper.
- Keep the existing license filter (`cc-by,cc-by-nc,cc-by-sa,cc-by-nc-sa,cc0`) on all
  photo fetches.
- No test framework exists yet.

## Approaches considered

| | Approach | Trade-off |
|---|---|---|
| A | Fully live: call iNat for pool, look-alikes and photos on every quiz | No data to maintain, but 30+ calls per quiz, slow, and down whenever iNat is |
| B | Curated JSON dataset generated by a script and checked in | Fast and controllable, but needs someone to curate and re-run it, and variety is frozen |
| **C (chosen)** | **Hybrid: slow-changing data (regional species pool, look-alikes) fetched through our API routes with ~daily server caching; photos fetched live** | Most of B's speed and reliability, no maintenance, fresh photos. Leaves room for a small hand-written override file later. |

The user picked C.

## Design

### Data the server provides (new API routes, each cached ~24h)

1. **Species pool** for a region and optional phylum filter. Built from
   `/v1/observations/species_counts` with `quality_grade=research`, the region bounds,
   and `iconic_taxa=Fungi` or `taxon_id`. Take roughly the top 200 species by count. Each
   entry has: taxon id, scientific name, common name, observation count, and
   **family id** (and genus id). The `ancestor_ids` don't say which ancestor is the family,
   so resolve ranks via `/v1/taxa?id=…` (it accepts comma-separated ids) and cache the
   result. "Worldwide" uses no bounds, and its global pool is treated like any other
  region: the full ramp, including hard and mastered, applies there too (user's decision).
2. **Look-alikes** for one species. Lazy, requested only when a species reaches the hard
   tier. From `similar_species?taxon_id=X`, keep only `rank === "species"` results,
   ordered by confusion count. Return the list. Filtering to the region happens on the
   client against the pool.
3. **Photos** for the species chosen for this quiz, in **one** call:
   `/v1/observations?taxon_id=a,b,c,…` with the existing quality, license, and photo filters
   **and the current region bounds**, as today, since appearance varies by region.
   Return at most one observation per species, and vary which observation you get between
   quizzes (random page or `order_by=random` if iNat supports it; builder verifies). Not
   cached.

The existing `/api/observations` and `/api/species-info` routes stay.

### Progress (client, localStorage)

A new key, e.g. `mycomatch.progress.v1`, separate from `quizState`:

```ts
interface SpeciesProgress {
  taxonId: number;
  tier: 0 | 1 | 2 | 3;      // 0 easy, 1 medium, 2 hard, 3 mastered
  streak: number;           // consecutive correct at current tier
  seen: number;
  correct: number;
  lastSeen: string;         // ISO date
  confusions: Record<number, number>; // taxonId picked instead -> count (for later spaced repetition)
}
```

Progress is keyed by taxon id and is **shared across regions and filters**. Knowing a
species doesn't depend on which region you're quizzing.

### Ramp rules (my calls; tune later)

- New species start at tier 0.
- **Promote** one tier after **2 consecutive correct** answers at the current tier.
  Two in a row keeps a single lucky guess from promoting.
- **Demote** one tier on a miss (minimum 0), and reset the streak.
- Tier 3, "mastered", means two in a row correct at hard. Mastered species are
  quizzed at the hard tier.
- Record the wrong pick in `confusions` on every miss.

### Distractors per tier

All distractors are species from the current pool, unless noted. Pick 3.

- **Tier 0 (easy):** species from a *different family* than the answer.
- **Tier 1 (medium):** species from the *same family*. Fill from the same order if there
  aren't enough. If still short, fall back to easy.
- **Tier 2–3 (hard):** look-alikes from the `similar_species` list, most-confused first,
  **preferring ones in the pool**. If fewer than 3 are in the pool, fill with
  **non-local look-alikes** from the same list (user's decision: real look-alikes beat
  same-family filler, even if they don't grow nearby). Non-local options get no
  special marking, since that would let learners eliminate them. Only when
  `similar_species` has fewer than 3 species-rank results in total, fill from the same
  genus, then the same family, then medium's rules.

Each question records which tier was *actually* used. Answers only promote or demote
based on the tier the species was supposed to be at. With the non-local fill, a hard
question only falls back to medium when iNaturalist has almost no confusion data for that
species. In that rare case, the answer still counts toward promotion. (My call: this keeps
those species from getting stuck.)

### Choosing which species go in a 10-question quiz

- About 60% **in progress** (tiers 0 to 2, already seen), least recently seen first.
- About 30% **new**: unseen species in pool order, most commonly observed first. This is
  how a beginner meets common local species before rare ones.
- About 10% **mastered** review.
- If any bucket is short, fill from the others. A first-time user gets 10 new, common
  species at tier 0.
- No duplicate species within a quiz.
- All buckets draw only from species in the current pool, since distractor selection
  needs the pool's family data.
- Varieties and subspecies in the pool are rolled up to their species.

### Quiz page changes

- Load flow: fetch the pool, choose species, fetch look-alikes for any hard-tier species
  (in parallel, cached), pick distractors, fetch photos in one call, then build the
  questions.
- On submit: update the species' progress (the score logic stays).
- Show a small tier label on each question, e.g. "New species", "Same family",
  "Look-alikes", so the learner understands why it got harder.
- Show a summary in the header and on the end screen: "12 mastered · 5 learning ·
  30 seen". On the end screen, call out which species got promoted.
- Remove the unused `difficulty` field from `QuizFilters`. Region and phylum filters stay.
- The tier label shows the tier actually used for the question's distractors.
- A resumed quiz keeps answered questions marked as answered. Otherwise a reload
  lets the learner answer again after seeing the answer and double-count toward
  promotion.
- Saved `quizState` from before this change has the old question shape. Give it a new
  key or version so stale state is discarded instead of crashing.
- Add a "Reset progress" action somewhere unobtrusive, such as the filters panel, with a
  confirm.

## Left to the builder

- Module layout (e.g. `lib/progress.ts`, `lib/distractors.ts`, `lib/selection.ts`) and
  route names.
- Exact pool size and cache TTLs, within the "~200 species, ~daily" intent.
- How to vary photos between quizzes.
- Loading and error states for the new fetches, and what to do when iNat fails
  (a cached pool should still allow a quiz if photos load).
- Whether to add a small test setup (e.g. Vitest) for the pure logic: ramp rules,
  distractor selection, species selection. Recommended, since this logic is easy to get
  subtly wrong and simple to unit test.
- Styling for the tier label and progress summary, matching the existing earthy theme.
